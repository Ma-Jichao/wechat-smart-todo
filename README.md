# wechat智能待办

在微信里用文字或语音记录事项，按时提醒，每天北京时间 08:00 汇总待办。单用户、自托管，源码可以交给自己的 AI 编程工具按需求修改。

## 功能

- 创建、查询、修改、完成和取消事项；时间不明确时追问。
- 今天、逾期、未定时间待办汇总；逾期事项保留到完成或取消。
- 每天固定一个或多个时间提醒；可选择仅中国工作日（含调休补班），或指定起止日期（如「从 10月1日 到 6日 每天 08:00」）。重复提醒不进早报、不标逾期。
- 微信服务端语音转写；纯文本消息，显示序号，不展示数据库内部 ID。
- 接收游标与消息同事务、发送队列、退避重试和崩溃恢复。

## 架构与部署方式

```text
微信 iLink
    ↕ wechatbot-sdk 的 ILinkApi（只作为协议层）
Python 单进程：接收 / 模型理解 / 统一发送 / 调度
    ↕ PostgreSQL 协议，127.0.0.1:5432
原生安装的 IvorySQL 5.6
```

运行环境沿用 Ubuntu 22.04、Python 3.10 虚拟环境、原生 IvorySQL 和 systemd。应用安装路径 `/opt/reminder-bot`，服务用户 `reminderbot`，数据库角色 `reminder`，业务对象在 `reminder` 库的 `bot` schema。主服务 `reminder-bot.service`，每日备份使用 `reminder-backup.timer`。

应用直接连接 iLink，不需要额外微信网关；SDK 负责协议，自研循环负责消息持久化。DeepSeek 的 Chat Completions + function calling 用于理解指令；更换兼容服务商需自行验证工具调用兼容性。

克隆本仓库并进入目录后，先查看计划：

```bash
bash deploy.sh --dry-run
```

在运行 systemd 的 Linux 服务器上以 root 执行安装：

```bash
bash deploy.sh
```

脚本检测已有原生 IvorySQL。已有实例时，验证管理员连接，并在明确同意后创建新的专用数据库和角色；没有实例时，先征求同意再安装官方原生 IvorySQL 5.6。用户提供自己的模型 API key，并在手机完成微信扫码。脚本随后应用迁移、配置现有形式的 systemd 主服务和备份定时器。

数据库安装和建库均须分别同意，脚本不能替用户完成扫码授权。支持情况、已有资产保护和安装中断处理见 [部署说明](docs/deployment.md)。全新系统完整安装与部分发行版仍待实测，具体见验证记录。

## 使用示例

- 提醒我明天下午三点开会
- 每个工作日早上八点十五提醒我打卡
- 从 10月1日 到 6日 每天八点提醒我更新汇报
- 今天有哪些待办
- 把开会改到后天上午十点
- 完成 2
- 先记着买牛奶，不用定时提醒

## 运维

安装完成后在服务器执行：

```bash
systemctl status reminder-bot.service
journalctl -u reminder-bot.service -n 50 --no-pager
cd /opt/reminder-bot
runuser -u reminderbot -- ./venv/bin/python -m app.main --status
runuser -u reminderbot -- ./venv/bin/python -m app.main --check
systemctl restart reminder-bot.service
```

手动备份：`/opt/reminder-bot/scripts/backup.sh`。默认每天 03:37 备份到 `/var/backups/reminder-bot`，保留 14 天。数据库含消息正文、账号标识与会话 token，备份属于敏感数据；同时将 `etc/` 加密备份到自己的受控存储。恢复先在独立数据库验证，不覆盖正在使用的数据库。

微信登录过期需本人重新扫码；重新绑定步骤见部署说明。主动发消息前需要用户先与机器人建立会话。

## 给 AI 的需求说明（可独立重新实现）

不想使用本仓库源码时，可以把本章交给自己的 AI 编程工具，从头实现。下面是项目作者最初需求与后续补充的整理版，不是聊天逐字记录；已去除私人部署信息。这些是需求和验收目标，不代表当前源码已全部满足，实际验证范围见 [验证记录](docs/verification.md)。

### 项目目标与范围

请实现一个名为「wechat智能待办」的单用户、自托管微信事项提醒系统。我会随时发语音或粘贴文字，告诉它什么时候提醒我做什么，也会继续修改、查询或完成这些事项。重点是事项不丢失、修改准确、主动提醒可验证。

当前范围包括一次性提醒、每天固定时间的重复提醒和每日待办汇总。多用户、群聊、图片 OCR、附件解析、网页后台、日历同步、复杂每周/月重复规则不在当前范围。不要自行扩展为通用助手，也不要替用户执行事项本身。

### 功能与交互

1. 支持文字和中文语音创建事项，粘贴内容后再补一句时间也能在有限上下文中关联。语音使用微信 iLink 服务端转写，不擅自接入第三方 ASR。转写缺失或不清楚时说明尚未记录，请用户澄清或改发文字。
2. 支持创建、查询、修改内容、修改时间、完成、取消，以及「先记着，不用定时提醒」。查询至少包括今天、逾期、未定时间及全部待办。
3. 相对时间按消息接收时刻和北京时间 `Asia/Shanghai` 解释；跨日重试不能改变「明天」的原意。缺时间、上午下午不明确、时间已过去、多个事项匹配时追问，不猜测、不静默顺延。
4. 只有数据库提交成功才回复操作成功，并回显事项和完整日期、星期、时间、时区，便于发现转写或理解错误。多事项输入应逐项说明哪些已保存、哪些仍待澄清。
5. 支持「推迟一小时」「把开会改到明天下午三点」「完成 2」「这个完成了」等表达。显示序号须绑定对应机器人消息中的事项，不能直接当数据库 ID；指向不明确时列候选询问。
6. 事项状态与投递状态分开。提醒发过不代表完成，发送失败也不能删除待办。完成和取消保留历史，并停止后续提醒；修改后旧版本的未发提醒必须作废，发送前再次检查状态和版本。
7. 支持每天一个或多个固定时间的重复提醒，以及仅中国工作日提醒：普通周末和法定节假日不发，调休补班日发。重复提醒只到点发送，不进入每日早报；日历依赖须说明覆盖年份和更新办法。

### 08:00 早报与消息呈现

1. 每天北京时间 **08:00** 主动发送一份逻辑早报，包含今天待办、逾期未完成和未定时间三类，未来日期事项通过查询查看。没有待办时给出明确提示。
2. **逾期事项一直保留，直到完成或取消；延期后按新时间处理。** 不因跨日、已提醒、重启或重试超限自动清理，不每隔几分钟反复催促。
3. 一次性事项在 08:00 到点时与早报合并，避免同内容连发。停机恢复后补发有效的一次性提醒和当天最新早报，标注补发及原定时间，不连续刷多天旧早报。
4. 汇总过长时分段并逐段跟踪，不截断或遗漏事项。补发前检查最新状态，避免继续发送已完成或旧版本内容。
5. 使用适合微信的纯文本：清单序号顶格、连续编号，小图标点缀，不显示内部 ID，不使用横线分隔或依赖 Markdown 渲染，不加个人称呼。事项点评独立成行。
6. 问候、逐条点评和结尾鼓励可由模型提供，内容、日期、数量和逾期天数由代码确定。模型措辞失败时使用固定文案，不能阻止早报发送。

### 架构、部署与运维

1. 保持 **原生 IvorySQL + Python 虚拟环境 + systemd**，不要擅自换成 PostgreSQL、Docker 或其它部署架构，也不要引入 Redis、消息中间件、Kubernetes 或额外微信网关。
2. 应用直接连接微信 iLink，SDK 只负责协议；单个 Python 异步进程实现接收、模型理解、调度和统一发送。模型理解新指令失败不能阻塞已有提醒与早报。
3. 提供一条命令启动的引导式部署脚本、只读预览模式和清晰的配置模板，尽量屏蔽 Linux 版本、包管理器及 CPU 架构差异。不支持的环境明确停止，并如实列出实测范围。
4. 先检测已有 IvorySQL；若有，在部署者明确同意后创建新的专用数据库和低权限角色；若没有，先征求同意再安装全新的原生 IvorySQL。安装与建库分别确认，不重建已有集群、不覆盖同名库或已有应用目录，不改动其它业务。
5. 使用者提供自己的模型 API key 和模型配置，微信扫码由本人完成。默认使用 DeepSeek 的工具调用理解指令；兼容接口可配置，但更换服务商须验证，不能假定所有模型兼容。
6. 使用低权限服务用户和数据库角色，数据库仅本地监听。给出状态、日志、重启、备份恢复及重新扫码说明；每日备份并在独立库实际恢复验证，凭据另行保护。
7. 备用告警通道暂不配置，提供日志和本地状态查看，并说明微信失效时无法主动告警的限制。不要自行发送邮件或购买服务。实施时不使用 `sudo`；破坏性操作须先列清单并取得同意。

### 一致性、恢复与安全

1. 接收消息可靠落库后才推进游标，消息、游标和必要会话状态保持事务一致。重复接收、模型失败、处理进程崩溃后能恢复，不重复创建事项，也不丢未处理指令。
2. 模型调用放在长数据库事务之外；业务变更、确认回复入队和处理成功标记保持原子性。模型仅可调用受控的事项工具，不提供任意 SQL、shell、文件或网络访问能力。
3. 确认回复、到点提醒、早报和错误通知共用持久化发送队列。具备业务去重键、发送租约、过期租约恢复、有限重试、退避和共享限流冷却，防止重试风暴和永久卡死。
4. 区分网络暂时故障、限流、登录或会话失效、永久错误和结果不确定的超时。认证或会话失效时暂停无效重试、保留队列；重试超限不能让待办消失。不要为测限流阈值持续加量。
5. 接口 `accepted` 只表示接口接受，不能写成用户实收。接口接受后、结果回写前崩溃可能重复发送，须说明和验证这个边界，不承诺端到端 exactly-once。
6. 只允许授权用户访问自己的事项。用户粘贴文字、语音转写和模型输出均为不可信输入，不能覆盖系统规则、越权或读取凭据；仅向模型发送理解指令所需的数据。
7. **公开仓库不得含任何个人信息或凭据**，包括真实 API key、token、数据库密码、私钥、账号标识、私人服务器信息、聊天记录、日志和备份。示例使用虚构内容与占位符；提交前检查暂存文件及将发布的 Git 历史。

### 验证与交付要求

交付源码、迁移、锁定依赖、配置模板、部署与运维说明，以及逐项验收结果。必须区分真实执行、模拟测试和待验证，说明验证在哪台机器、是否使用隔离库；不自行在生产环境部署、发送真实微信测试消息或调用付费模型，相关验证应另获使用者授权。

验收至少覆盖：文字/语音完整创建链路、歧义澄清、修改与完成后的旧提醒作废、显示序号不串项、重复消息与崩溃恢复、限流和认证失效、早报分组与跨日逾期保留、08:00 合并、停机补发与长消息分段、调休工作日重复提醒、低权限及备份恢复，以及安装/建库拒绝和已有资产保护。

**真实主动推送必须单独验收**：程序重启后不由用户先发消息，以及隔夜无互动后的 08:00 早报，都要记录计划时间、接口结果和用户实收。服务 `active`、模拟成功或一次即时回复都不能替代实收验收；若平台不支持，应如实报告限制，不能靠要求用户每天先发消息来宣布需求完成。

## 已知限制与验证

- **主动推送依赖近期入站消息**：连续多日不互动（典型如国庆长假）时，iLink 的 `sendmessage` 会返回 `prepare failed`，提醒与早报进入 `blocked_context`，**不按原定时间送达、但不会丢**，等你下一条消息到达后再按序补发。可持续主动推送的时间边界未确定，不能保证隔夜送达；长假等场景若要按时提醒，建议每天给机器人发一条消息保持通道活跃。
- `accepted` 仅表示接口接受，不是用户送达/已读回执。接口接受后、结果回写前崩溃可能重复发送，不宣称端到端 exactly-once。
- 语音转写可能出错；图片、附件、群聊、多用户、复杂每周/月规则尚不支持。
- 中国节假日数据依赖 `chinesecalendar`，当前锁定版覆盖至 2026 年，后续年份需更新并测试。
- 无备用告警通道；微信登录过期需要本人重新扫码。
- 测试与未完成验收见 [验证记录](docs/verification.md)。
